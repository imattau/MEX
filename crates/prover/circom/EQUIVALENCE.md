# dex_batch.circom <-> DEXBatchCircuit equivalence

Stage P6-1b of the ZK trusted-setup-ceremony effort. `dex_batch.circom`
is a port of `crates/prover/src/lib.rs`'s `DEXBatchCircuit<F>` (an
arkworks `ConstraintSynthesizer`). Once a ceremony runs, it runs against
*this circom file*, not the Rust struct -- so the whole point of this
document is establishing, as rigorously as practical, that the two
actually encode the same constraint system before that happens. A
ceremony run against a circuit that's subtly different from what
`crates/prover` actually proves/verifies would be worthless (or worse,
misleading) security theater.

Two independent checks, neither alone sufficient, together reasonably
strong:

## 1. Structural equivalence (counts)

`cargo test -p prover test_constraint_counts_match_the_circom_port`
asserts the arkworks circuit produces exactly:

- 32 constraints (circom: 8 non-linear + 24 linear = 32)
- 3 instance variables (circom: 2 public inputs + the implicit
  constant-one wire every R1CS system has)
- 63 witness variables (circom: 55 declared private inputs -- six
  8-element arrays plus 7 intermediateRoots -- + 8 internal `val`
  signals arkworks' flat witness-variable model counts but circom's
  "private inputs" figure, which only counts declared circuit inputs,
  doesn't)

Matching counts are necessary but not sufficient for equivalence (two
different constraint systems could coincidence-match on size) -- but a
MISMATCH would be conclusive proof of inequivalence, so this is a cheap,
meaningful first gate. Requires no external tooling, runs in `cargo
test`.

## 2. Witness-level cross-check (same fixture, both implementations)

`./check_equivalence.sh` (requires `circom` and `snarkjs` on PATH --
deliberately NOT part of the default `cargo test` toolchain, see the
script's own header) runs the *exact same* numeric fixture
`crates/prover/src/lib.rs`'s `batch_circuit_one_real_trade` test helper
uses (one real trade: makerPre=5, takerPre=10, amount=2, price=3 ->
makerPost=11, takerPost=4, root 0->6; padded with 7 no-op trades) through
the compiled circom circuit's witness generator, and confirms:

- `input_valid.json` (the correct values) produces a witness satisfying
  all 32 constraints (`snarkjs wchk` reports "WITNESS IS CORRECT") --
  matching `test_zk_circuit_satisfied`.
- `input_tampered.json` (makerPost=99 instead of 11, matching the Rust
  test's own tamper) fails witness generation at a constraint assertion
  -- matching `test_zk_circuit_unsatisfied_tampered_post_balance`'s
  expectation that this witness is UNSATISFIABLE.

This is real evidence the two implementations agree on both what's
valid and what's specifically invalid, not just that they happen to
have the same size.

## What this does NOT prove

Neither check is a formal proof of full semantic equivalence across
EVERY possible input -- that would need either a symbolic/algebraic
comparison of the two constraint systems' actual A/B/C matrices (not
done here; `cargo test`'s count-based check plus one concrete witness
pair is the level of rigor this stage reaches) or a much larger
randomized/property-based cross-testing campaign across many witness
values. Before a real ceremony runs, more witness fixtures (varied
amounts/prices/multiple real trades in one batch, not just the single
one checked here) should be cross-tested the same way, and ideally a
direct R1CS matrix diff should be attempted using `ark_relations`'s
`ConstraintSystem::to_matrices()` against circom's `.r1cs` binary
format.

## Reproducing

```sh
cd crates/prover/circom
./check_equivalence.sh
```

Compiled artifacts (`dex_batch.r1cs`, `dex_batch.sym`, `dex_batch_js/`,
`*.wtns`) are build outputs, regenerated by the script -- not committed
(see `.gitignore` in this directory). Only the circom source, this
document, and the two input fixtures are checked in.
